# Журнал архитектурных и проектных решений

## 1. Назначение документа

В этом файле фиксируются согласованные решения по архитектуре, математической модели, технологиям и организации разработки.

При изменении решения необходимо указать причину, последствия и дату. История прежних решений сохраняется.

Приоритет документации:
1. `docs/model.md` — математическая модель и границы её применимости.
2. `docs/decisions.md` — утверждённые проектные и архитектурные решения.
3. `docs/state.md` — текущее состояние и порядок работ.
4. `docs/divergences.md` — список выявленных расхождений и статус их устранения.

После исправления расхождений `docs/divergences.md` актуализируется, чтобы выполненные пункты не оставались в нём как незакрытые задачи.

## 2. Принятые решения

### D001. Язык программирования

**Решение:** Python 3.13.

Язык используется для реализации доменной модели, расчётной логики, алгоритмов оптимизации, автоматических тестов и веб-интерфейса.

### D002. Библиотеки и управление зависимостями

**Решение:** использовать следующий стек:

- NumPy — численные расчёты;
- Pandas — обработка табличных данных;
- Matplotlib — визуализация;
- pymoo, NSGA-II — многокритериальная оптимизация;
- Flask — веб-интерфейс;
- SQLite — локальное хранение данных;
- pytest — автоматические тесты.

DEAP не входит в основной стек. Файл `notebooks/deap_onemax.py` сохраняется как учебный пример и требует установленной библиотеки DEAP для запуска.

**Версии зависимостей:**
- `pyproject.toml` содержит явные диапазоны совместимых версий основных зависимостей;
- `requirements-lock.txt` содержит точные версии библиотек, включая транзитивные зависимости, для воспроизводимой установки;
- файлы зависимостей должны соответствовать выбранной версии Python и проверенному окружению проекта;
- закрепление версий выполняется на основании активного `.venv`, а не глобального Python.

### D003. Модель судна и расчёт остойчивости

**Решение:** реализовать собственную упрощённую аналитическую модель остойчивости с использованием NumPy.

Для первой версии используется синтетическое судно с идеализированным корпусом типа box-barge. Руководитель разрешил использовать синтетические значения основных характеристик судна, включая длину, ширину, массу порожнего судна и координаты его центра тяжести.

**Обязательные параметры синтетического судна:**

- `synthetic` — явный флаг синтетического набора параметров; для текущего проекта значение должно быть `true`;
- `length_m` — длина судна;
- `beam_m` — ширина судна;
- `lightship_mass_kg` — масса порожнего судна;
- `lightship_cg_x_m`, `lightship_cg_y_m`, `lightship_cg_z_m` — координаты центра тяжести порожнего судна.

Эти параметры обязательны в `configs/vessel.json`. Отсутствие флага `synthetic` или любого обязательного параметра должно приводить к ошибке загрузки конфигурации. Значения нельзя подставлять скрытыми значениями по умолчанию.

Все синтетические характеристики должны быть явно обозначены и документированы. Если в будущем будет использоваться реальное судно, его характеристики должны подтверждаться соответствующими техническими данными, а не переноситься из синтетического сценария.

Модель ограничена принятыми геометрическими и физическими допущениями:
- корпус представлен упрощённой геометрией box-barge;
- гидростатические показатели вычисляются только в пределах реализованных аналитических зависимостей и при наличии необходимых входных данных;
- модель малых углов применима только при \(|\varphi| \leq 5^\circ\);
- для углов за пределами этого диапазона результат не должен выдаваться как достоверный;
- ограничения модели и синтетический характер исходных параметров должны быть отражены в документации и интерпретации результатов.

Модель не является полноценной инженерной системой подтверждения безопасности реального судна.

### D004. Оптимизационный алгоритм, декодер и оценка плана

**Решение:** использовать pymoo с алгоритмом NSGA-II для многокритериальной оптимизации.

Предварительное представление решения — перестановка индексов контейнеров. Индекс в перестановке не является идентификатором контейнера.

**Декодер** преобразует перестановку контейнеров в план размещения по грузовым позициям. Декодер не должен самостоятельно пересортировывать перестановку: это меняло бы смысл особи NSGA-II.

Эвристический алгоритм может использовать тот же механизм размещения, но задавать свой порядок обработки контейнеров, например сортировать их по убыванию массы. Эвристика с сортировкой и декодер перестановки NSGA-II являются разными стратегиями формирования входного порядка.

**Физические проверки размещения:**
- находятся в `src/stowage/model/`;
- проверяют, свободен ли слот;
- проверяют наличие допустимой опоры и ограничения штабелирования;
- проверяют допустимость нагрузки на колонну и bay;
- предоставляют повторно используемые функции, а не дублируемые правила.

Декодер вызывает эти функции и использует их результаты, но не реализует те же проверки независимо вторым способом.

**Глобальная оценка плана:**

Функция оценки задачи оптимизации `evaluate()` получает сформированный план и использует расчётные модули для оценки глобальных показателей, включая GM, крен и дифферент. Эти показатели не должны рассчитываться отдельной копией физической модели внутри декодера.

Ограничения pymoo записываются в принятом соглашении \(g_i(x) \leq 0\). Для каждого ограничения необходимо явно определить формулу и единицы измерения. Минимальный GM, предельный крен, дифферент и неразмещённые контейнеры могут быть представлены ограничениями или целевыми функциями в соответствии с формализацией T05.

Окончательные кодирование решения, состав целевых функций, обработка недопустимых планов и стратегия выбора слотов уточняются до реализации оптимизационного алгоритма.

Выбор слотов должен быть проверен отдельно: заполнение первого свободного слота может привести к нежелательному смещению распределения груза вдоль судна. Разработка и проверка стратегии размещения относится к этапу алгоритмов T11–T17.

### D005. Порты и нормализация названий

**Решение:** базовая последовательность портов:

**Калининград → Санкт-Петербург → Мурманск.**

Каноническое название второго порта — `Санкт-Петербург`.

Сокращения и альтернативные варианты названий задаются в `configs/ports.json` через словарь псевдонимов, например:

`"Санкт-Петербург": ["СПб"]`

При чтении исходных данных известный псевдоним преобразуется в каноническое название. Исходный CSV не изменяется.

Неизвестный порт должен вызывать понятную ошибку проверки данных. Нельзя молча сохранять неизвестное значение, автоматически подменять его другим портом или удалять контейнер из набора.

Маршрут и псевдонимы хранятся в конфигурации, а не фиксируются непосредственно в алгоритмах размещения.

### D006. Типы контейнеров

**Решение:** первая версия поддерживает типы `dry`, `tank` и `reefer`.

Типы и их настраиваемые характеристики должны быть расширяемыми. Основные алгоритмы размещения не должны зависеть от жёстко зашитого перечня типов.

В первой версии тип контейнера сам по себе не меняет физическую модель размещения. Специальные технологические ограничения могут добавляться отдельно после уточнения требований.

### D007. Идентификаторы контейнеров

**Решение:** ID контейнера — целое число `int`, не меньше нуля. ID `0` допустим.

ID должны быть уникальными в пределах одного набора данных.

ID контейнера и индекс контейнера в перестановке оптимизатора — разные понятия. Индекс используется для адресации элемента перестановки, ID — для идентификации самой сущности.

При чтении CSV необходимо явно задавать целочисленный тип для поля ID, например `dtype={"id": "int64"}` при использовании Pandas. После чтения проверяются целочисленность, неотрицательность и уникальность идентификаторов.

В доменном слое для проверки целочисленных значений используется общий валидатор на основе numbers.Integral. Допускаются обычные целые числа Python и совместимые целочисленные скалярные типы NumPy. Значения bool и numpy.bool_ отклоняются. После проверки разрешённое значение приводится к обычному Python int. Не допускается неявное преобразование float или str в целое число. Это же правило применяется к индексам грузовых позиций, размерностям сетки судна и ID в назначениях плана.

Нельзя использовать проверку истинности вида `if not container.id` для определения отсутствующего ID: она ошибочно считает значение `0` отсутствующим.

### D008. Конфигурация проекта

**Решение:** параметры судна, нагрузок и глобальные пороги хранятся в отдельных JSON-файлах:

- `configs/vessel.json` — параметры судна, геометрия грузовой сетки, характеристики порожнего судна, синтетические параметры и ограничения нагрузки, привязанные к геометрии судна;
- `configs/limits.json` — универсальные пороги модели, в частности минимальный и целевой GM, предельный крен и дифферент, а также общие ограничения груза, не зависящие от конкретной геометрии судна;
- `configs/ports.json` — канонические названия портов, псевдонимы и последовательность портов.

Размерность сетки задаётся параметрами `bays`, `rows`, `tiers`. Конфигурация 8 × 4 × 3 является одним из тестовых сценариев, а не универсальной геометрией всех судов.

Лимиты по нагрузке на bay и колонну задаются в `vessel.json`, так как зависят от конфигурации судна. Значения для одной геометрии нельзя автоматически переносить на другую.

Загрузчик должен валидировать наличие обязательных параметров, их типы и допустимые значения. Отсутствующие обязательные параметры должны приводить к понятной ошибке, а не к незаметному использованию значений по умолчанию.

### D009. Архитектурное разделение

**Решение:** разделить проект на доменную модель, расчётное ядро, алгоритмы, сервисный слой, хранилище и веб-интерфейс.

Предполагаемая структура:

- `src/stowage/domain/` — доменные сущности;
- `src/stowage/model/` — физические расчёты и проверки размещения;
- `src/stowage/algorithms/` — оптимизационные алгоритмы и декодирование;
- `src/stowage/datagen/` — генерация тестовых данных;
- `src/stowage/services/` — прикладные сервисы;
- `src/stowage/storage/` — взаимодействие с SQLite;
- `src/stowage/viz/` — визуализация;
- `src/stowage/web/` — веб-интерфейс.

Доменный слой не зависит от NumPy, Pandas, Flask, базы данных или оптимизационного алгоритма. Расчётные модули могут использовать NumPy. Веб-интерфейс обращается к прикладной логике через сервисный слой.

### D010. Тестирование

**Решение:** использовать pytest.

Автоматические тесты необходимы для:
- доменных сущностей;
- загрузчика конфигурации;
- генератора данных;
- физических расчётов;
- проверки нагрузок и допустимости плана;
- декодера;
- целевых функций и ограничений оптимизатора.

Расчётные формулы проверяются на тестовых примерах с известным результатом и на граничных случаях.

Команда запуска тестов:

`python -m pytest -v`

Smoke-тест подтверждает базовую установку и импорт пакета, но не доказывает корректность математической модели.

### D011. Ограничения моделирования типов контейнеров

**Решение:** в первой версии не моделируется дополнительное влияние свободной поверхности жидкости в танк-контейнерах.

Также не моделируются требования к электрическому питанию рефрижераторных контейнеров.

Это ограничения текущей модели, а не утверждение об отсутствии таких эффектов в реальной эксплуатации. Они должны быть явно отражены в документации и при интерпретации результатов.

### D012. Грузовая сетка и ограничения нагрузок

**Решение:** размерность грузовой сетки задаётся параметрами судна: `bays`, `rows`, `tiers`.

Термины модели:
- **bay** — совокупность всех слотов с одинаковым индексом bay; для сетки с четырьмя рядами и тремя ярусами один bay включает 12 слотов;
- **колонна** — совокупность слотов с одинаковыми индексами bay и row по всем ярусам; при трёх ярусах одна колонна включает 3 слота.

Ограничения по нагрузке на bay и колонну находятся в `vessel.json` и привязываются к соответствующей конфигурации судна или тестового сценария.

Предварительные значения 220 т на bay и 60 т на колонну относятся к сценарию с тремя ярусами. Они не должны автоматически применяться к конфигурации с четырьмя ярусами или иной геометрией. Для другой конфигурации требуются отдельные значения и обоснование.

В коде и конфигурации единицы должны быть указаны явно. Если нагрузка задаётся в тоннах, имя параметра должно иметь суффикс `_t`; если в килограммах — `_kg`. Преобразование выполняется явно на границе загрузки или расчёта.

### D013. Единицы измерения и названия полей

**Решение:** единицы измерения должны быть явными и согласованными.

Для массы контейнера в доменной модели используется поле `mass_kg`, не `weight_kg`. Аналогично, масса порожнего судна задаётся полем `lightship_mass_kg`.

В исходном CSV сохраняется исторический столбец `weight`. При чтении данных столбец `weight` преобразуется в поле `mass_kg`. Сам эталонный CSV не переименовывается и не редактируется.

Для других величин единицы также указываются явно:
- масса — `_kg` или `_t`;
- линейные размеры и координаты — `_m`;
- углы — `_deg`;
- относительный дифферент — согласованная безразмерная доля или процент с явным описанием.

При расчётах величины в разных единицах не сравниваются напрямую. Преобразование выполняется явно в определённом месте программы.

### D014. Проверка исходных данных и конфигурации

**Решение:** проверять входные данные до запуска расчётов и оптимизации.

Проверяются:
- наличие обязательных полей;
- корректность типов и допустимых значений;
- целочисленный неотрицательный ID и уникальность идентификаторов;
- положительная масса контейнера и её соответствие ограничениям;
- распознавание портов через канонические имена и разрешённые псевдонимы;
- согласованность типов контейнеров с конфигурацией;
- существование и допустимость грузовых позиций;
- согласованность параметров судна и геометрии сетки;
- наличие флага `synthetic` и всех обязательных параметров для выбранного типа конфигурации;
- отсутствие неявной подстановки отсутствующих значений.

В текущем проекте синтетическая конфигурация должна явно содержать `"synthetic": true` и все обязательные синтетические параметры. Отсутствие флага или обязательных полей приводит к ошибке загрузки.

Если конфигурация помечена как реальная, синтетические параметры не должны использоваться вместо отсутствующих подтверждённых технических данных.

Ошибки входных данных должны приводить к понятным сообщениям, а не к скрытому изменению или пропуску данных.

Для синтетического судна параметры выбираются как синтетические и маркируются соответствующим флагом. Это не означает, что выбранные параметры описывают реально существующее судно.

## 4. Дополнительные решения D015–D020

### D015. Система координат и индексация

**Решение:** индексы грузовых позиций начинаются с нуля (`0-based`).

Система физических координат:
- начало координат расположено на базовой плоскости у кормового конца судна на диаметральной плоскости;
- ось X направлена от кормы к носу;
- ось Y имеет нулевое значение на диаметральной плоскости и положительное направление к правому борту;
- ось Z направлена вверх от базовой плоскости.

Индекс row увеличивается от левого борта к правому; фактическая координата Y определяется геометрией грузовой сетки и должна учитывать положение диаметральной плоскости.

Положительный угол крена означает крен на правый борт. Положительный дифферент означает наклон носом вниз. Эти знаковые соглашения должны одинаково использоваться в расчётах, визуализации, тестах и документации.

Геометрия судна должна учитывать:
- `first_bay_offset_m` — продольное смещение центра первого bay относительно начала координат;
- `base_height_m` — высоту базового уровня размещения нижнего яруса относительно базовой плоскости.

Координаты слотов вычисляются с учётом этих смещений и заданной геометрии сетки. Нельзя предполагать, что начало координат автоматически совпадает с центром первого bay или нижней плоскостью контейнера.

### D016. Порядок реализации T02, T04 и T03

**Решение:** JSON-конфигурации можно подготовить до T02, но загрузчик, который создаёт объект `Vessel`, реализуется только после готовности доменной модели.

Порядок работ:
1. Подготовить JSON-файлы конфигурации — фаза A T04.
2. Реализовать шесть доменных сущностей T02.
3. Реализовать загрузчик конфигурации — фаза B T04.
4. Реализовать генератор данных T03.

T03 зависит от готовой доменной модели T02 и необходимых конфигурационных файлов T04. Загрузчик `Vessel` не является обязательным условием для самого генератора, если генератору достаточно конфигурации контейнеров, типов и портов.

### D017. Границы T06, T07 и T08

**Решение:** разделить обязанности расчётных задач.

- **T06 — центр тяжести:** расчёт суммарной массы и координат центра тяжести системы «судно — груз». Используются масса и координаты центра тяжести порожнего судна из `vessel.json` и известные координаты размещённых контейнеров.
- **T07 — гидростатика и остойчивость:** расчёт доступных показателей упрощённой модели, включая осадку, KB, BM, GM, крен и дифферент. Используются необходимые геометрические параметры, масса и центр тяжести. Для текущей синтетической модели требуемые исходные параметры должны присутствовать в конфигурации или быть явно и проверяемо вычисляемыми по принятой аналитической модели.
- **T08 — ограничения плана:** проверка допустимости размещения, занятости слотов, допустимой опоры, массы контейнеров и нагрузок на bay и колонну.

Синтетические характеристики судна разрешено задавать для учебного сценария, но они должны быть явно обозначены и присутствовать в `vessel.json`. Расчётная модель должна отличать такие параметры от характеристик реального судна.

Проверка геометрических и нагрузочных ограничений не заменяет расчёт остойчивости. Расчёт остойчивости не должен выдаваться за подтверждение безопасности реального судна.

### D018. Воспроизводимость генерации данных

**Решение:** генератор тестовых данных принимает явный параметр `seed` и использует отдельный экземпляр `random.Random(seed)`.

При одинаковых параметрах генерации и одинаковом seed результат должен быть воспроизводимым. Нельзя полагаться на глобальное состояние генератора случайных чисел.

Генератор T03 не должен перезаписывать `data/containers.csv` без явного указания пользователя. Эталонные данные хранятся отдельно в `data/samples/containers_legacy.csv`.

### D019. Хранилище данных

**Решение:** использовать SQLite для локального хранения данных на этапе реализации хранилища.

Взаимодействие с базой данных изолируется в `src/stowage/storage/`. Доменная модель и расчётное ядро не должны напрямую зависеть от SQLite.

### D020. Каталог результатов

**Решение:** визуализации и результаты экспериментов сохраняются в `results/`.

Каталог `result/` заменяется на `results/`. Все пути сохранения и ссылки в документации должны соответствовать новому имени. Результаты не должны сохраняться внутри пакета `src/stowage/`.

## 5. Правила изменения решений

1. Не менять согласованные решения молча.
2. При изменении решения указывать причину и влияние на код, тесты и документацию.
3. Сохранять историю прежних решений.
4. Сверять архитектуру с `docs/model.md` и актуальным состоянием `docs/state.md`.
5. Синтетические параметры судна разрешены только в явно маркированной синтетической конфигурации.
6. Не подменять отсутствующие обязательные параметры скрытыми значениями по умолчанию.
7. Не считать успешный smoke-тест доказательством корректности математической модели.
8. Не переносить физические проверки из `model/` в дублирующую реализацию внутри декодера.
