
# AGENTS.md — правила работы Codex

## 1. Основной принцип

Это учебный дипломный проект. Приоритеты: работающее приложение, корректная математика, простой и понятный Python-код, который студент сможет самостоятельно объяснить на защите.

Не усложняй реализацию без необходимости.

## 2. Порядок работы

Перед каждой задачей:

1. Прочитай `PROJECT_CONTEXT.md` и относящиеся к задаче локальные файлы проекта и документации.
2. Проверь текущую Git-ветку, `git status` и существующие незакоммиченные изменения.
3. Предложи короткий план: какие файлы потребуется изменить, что реализовать и какими тестами проверить.
4. Дождись явного согласования пользователя.

Не выходи за пределы согласованной задачи. Если потребовались дополнительные изменения, сначала запроси разрешение.

### Режимы работы

**Режим 1 — чтение (по умолчанию)**

Разрешено читать локальные файлы, изучать код и тесты, выполнять `git status`, `git diff` и предлагать решения.

Запрещено изменять файлы и запускать команды с побочными эффектами.

**Режим 2 — проверки (после разрешения)**

Разрешено запускать согласованные проверки, включая pytest, с использованием существующего `.venv`.

Учитывай, что Python, pytest и тесты могут создавать `.pytest_cache/`, `__pycache__/` и другие файлы. Перед запуском оцени возможные побочные эффекты. Не удаляй временные или пользовательские файлы без разрешения.

**Режим 3 — изменения (после согласования плана)**

Разрешено изменять только согласованные файлы и функциональность.

Коммиты, переключение веток, push и удаление файлов требуют отдельного разрешения.

Не переходи между режимами самостоятельно.

## 3. Требования к коду

- Используй существующую архитектуру, сущности и утверждённые библиотеки.
- Выбирай самое простое корректное решение.
- Предпочитай небольшие функции, понятные названия переменных и прямые алгоритмы.
- Не добавляй лишние классы, интерфейсы, абстракции, шаблоны проектирования и слои.
- Не выполняй массовый рефакторинг и косметические изменения вне задачи.
- Не добавляй зависимости без отдельного разрешения.
- Не дублируй существующие расчёты и проверки.
- Сохраняй совместимость с действующими интерфейсами и тестами.

Перед изменением существующего кода оцени его только в пределах текущей задачи:

- Нет ли избыточной сложности?
- Нет ли дублирования вычислений и проверок?
- Нет ли ненужных классов и абстракций?
- Можно ли упростить реализацию без потери корректности?

Предлагай обоснованные упрощения, но не выполняй их без согласования.

Полный аудит репозитория проводится только по отдельному запросу пользователя.

## 4. Архитектура и математика

- `src/stowage/domain/` — доменные сущности без зависимостей от численных библиотек, базы данных и веб-интерфейса.
- `src/stowage/model/` — физические расчёты и проверки размещения.
- `src/stowage/algorithms/` — алгоритмы размещения и оптимизации.
- Остальные модули сохраняют назначение из `docs/decisions.md`.

Математические формулы и допущения бери из актуального локального `docs/math_model.md`, сверяя их с `docs/model.md` и принятыми решениями.

Сохраняй систему координат, единицы измерения и параметры конфигурации. Не подставляй скрытые значения по умолчанию вместо обязательных параметров.

Для каждого нового физического расчёта подготовь понятное объяснение, числовой пример и тест с известным результатом.

При обнаружении противоречия в документации не выбирай решение самостоятельно — сообщи пользователю.

## 5. Защита данных и изменений

- Не перезаписывай пользовательские незакоммиченные изменения.
- Не используй `git reset --hard`, `git clean`, `git restore`, `git checkout --` или `git stash` для удаления либо скрытия пользовательских изменений без отдельного согласия.
- Особое внимание уделяй локальным изменениям `docs/math_model.md`.
- Не перезаписывай исходные и эталонные CSV-файлы.
- Не запускай устаревшие скрипты из `legacy/` вместо актуальной реализации.
- Не переключай ветки, не создавай коммиты и не выполняй `git push` без явного разрешения.
- Не редактируй документацию вне согласованной задачи.

Локальные файлы являются основным источником для проверки текущего рабочего дерева.

Если локальный файл недоступен для чтения:

1. Явно сообщи об этом пользователю.
2. Не утверждай, что проверил его содержимое.
3. Не выдавай версию файла на GitHub за локальную.
4. Не изменяй этот файл и зависящий от его непроверенного содержимого код до уточнения.

## 6. Окружение и тестирование

Используй существующее `.venv` проекта на Windows 11 с Python 3.13.2.

Не создавай новое окружение и не используй глобальный Python вместо проектного.

Команда полного запуска тестов:

`.\.venv\Scripts\python.exe -m pytest -q`

Запускай тесты только в разрешённом режиме проверок или в рамках согласованного плана изменений.

Перед запуском учитывай возможное создание кэша и другие побочные эффекты тестов.

После изменения кода:

1. Добавь или обнови необходимые тесты.
2. Проверь числовые примеры и граничные случаи.
3. Запусти полный набор тестов.
4. Сообщи фактический результат.

Не считай успешный запуск тестов доказательством математической корректности без проверки ожидаемых результатов.

Не утверждай, что тесты прошли, если они не запускались.

## 7. Отчёт после выполнения

Кратко сообщи:

- Какие файлы изменены и зачем.
- Как работает реализация простыми словами.
- Какие тесты запускались и их результаты.
- Какие ограничения или нерешённые вопросы остались.

Покажи результат пользователю для проверки. Не выполняй коммит автоматически.

**Главное правило: минимальные согласованные изменения, понятный код, корректные расчёты и обязательная проверка результата.**
